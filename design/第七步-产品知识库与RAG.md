# 第七步：产品知识库与 RAG

**状态（2026-09-12）：经 ponytail 精简的首版设计，尚未实现。** 首版优先满足售后需求，使用现有 PostgreSQL 加 pgvector；Milvus 是后续可选替换。保留前轮调研结论，具体 embedding 模型与预算在实现前结合资料和运行资源选择。

## 1. 首版要解决什么

用户说“S1 Pro 不吸了”，图片里可能有故障码。系统需要确认产品、找到适用资料、补齐操作前提，再给出有依据的指导。检索相似度高不能代替产品身份、版本与安全条件检查。

**最小链路：确认产品 → 限定资料范围 → 精确线索查询／语义检索 → 补齐必要上下文 → 返回证据。** RAG 提供依据，原有 Agent 循环决定追问、指导或升级；保留现有 11 个工具。

语义检索用于匹配消费者口语和手册术语；产品、故障码等明确标识用结构化字段查询。首版不默认加入 BM25、RRF、独立重排模型或检索结果缓存。

## 2. 知识怎么组织

| 对象 | 最小内容与作用 |
|---|---|
| 产品目录 | 产品 ID、品牌、型号、别名、产品类型及地区变体；服务全产品，不按产品复制 Agent |
| 文档版本 | 来源、内容哈希、适用产品、地区／渠道、固件范围、生效条件与审核状态 |
| 章节／片段 | 正文、标题路径、父章节 ID、页码／位置、表格图片引用、向量 |
| 已审核步骤 | 步骤 ID、来源版本、前置条件、警告、预期反馈；供受控操作卡使用 |

产品目录与资料映射可先由维护者核对后导入。一份手册关联多个产品时共用正文；章节有更窄条件时继续收窄。同型号不等于同一台设备，设备归属仍由业务状态和 Memory 管理。

技术资料、政策和已审查的脱敏经验按类型区分。个人聊天、订单和凭证走原有业务查询。政策按地区、渠道及购买／事件时间匹配，不能直接取最新文件；语言不作为销售地区的替代依据。

**资料前提：** 当前尚无安克全量知识，覆盖率单独披露；缺适用范围或审核依据的资料不发布。资料缺失时继续澄清或升级，不能因此预先限制产品服务范围。

## 3. 入库：一个离线导入脚本即可

**核对来源与范围 → 整理章节 → 生成片段和向量 → 检查 → 发布。** 首版无需导入平台、定时全网抓取或复杂任务编排。

- 清晰的 Markdown／文本直接按标题处理；PDF 或扫描手册需要时使用 Docling 解析，保留页码、图片及表格关系。关键型号、故障码、数值和警告人工核对，失败保留原件并标记缺失。
- 短章节直接作为检索单元，只有超长章节才切成带父章节 ID 的片段。表格保留表头、单位、注释；前置条件和安全警告不能在切分时丢掉。
- 用原文加已核对的标题、型号构造 embedding 输入。保留原始片段作为引用，不让模型补造技术事实；暂不批量生成假想问答。
- 正文、向量和版本状态放在同一个 PostgreSQL。模型调用在事务外完成，新版本准备好后通过短事务发布；失败时旧版继续可用。旧版本按适用时间保留或撤回，无需首版处理跨数据库同步。

公开资料中的操作步骤也要经过项目审核；自动抽取只产生候选，未审核步骤不能用于实际操作卡。

## 4. 检索与主循环如何衔接

```mermaid
flowchart LR
    A[问题与图片观察] --> B[产品候选与确认]
    B --> C[服务端限定适用资料]
    C --> D[精确线索查询及语义补充]
    D --> E[片段去重与必要章节展开]
    E --> F[证据、来源与缺项]
    F --> G[原有 Agent 循环]
```

**先消歧。** `resolve_product` 查标准型号和别名，图片观察只提供线索；用户确认或已核验记录完成产品绑定。产品不明时先问能区分候选的问题，不跨产品推荐操作。

**再过滤。** `search_knowledge` 接收问题和类型，服务端注入身份、已确认产品和已知适用条件，使用参数化查询。缺少会影响答案的字段才追问；例如固件未知时，只能直接采用明确不依赖固件版本的指导。

**精确线索优先，语义补充。** 明确故障码先查对应条目；无明确线索或返回不足时，在同一授权、适用范围内按向量距离取有限片段。保留原始故障码，按片段 ID 去重；排序与候选数量由服务端控制，不引入分数融合调参。精确命中也要检查是否支持当前问题，证据不足可继续语义补查。

**按需展开。** 短章节直接返回；命中长章节的子片段时补齐相关前提和警告，其余长正文交第五步按需读回。父块缺失或必要条件尚未读取，不用孤立句子指导操作。

**返回证据。** 沿用工具契约，包含片段／步骤 ID、版本、来源页码、适用条件与未核实项，区分无结果和接口故障。主循环判断是否足以继续；冲突无法核清时澄清或升级。距离分数不当正确率，有引用也不能保证自由文本回答正确。

图片仍通过 `inspect_image` 实际读取。用户故障图用于提取可见线索，手册图用授权材料 ID 按需查看；保留原图，暂不建立独立视觉向量索引。补查继续计入现有运行预算，不新增检索 Agent 或反思循环。

## 5. ponytail 检查：保留什么，什么时候再加

| 设计项 | 首版选择 | 增加复杂度的依据 |
|---|---|---|
| 向量存储 | PostgreSQL + pgvector，与业务数据库共用部署 | 检索负载需独立扩容，或出现明确的 Milvus 学习／部署任务时再比较 |
| 向量索引 | 范围过滤后使用精确近邻查询；保留普通关系索引 | 实测检索延迟超出项目目标时，先评估 pgvector 的近似索引 |
| BM25／RRF | 暂不实现 | 评测发现技术词项漏召回，且现有精确字段与语义检索不能解决 |
| 独立重排模型 | 暂不实现 | 正确片段已在候选中，但频繁排不进上下文预算 |
| 检索缓存 | 暂不实现；Redis 继续承担既有唤醒等职责 | 重复查询造成可测延迟或成本，收益值得增加失效逻辑 |
| 解析与分块 | 离线脚本、章节优先，长章节才分子块 | 复杂版式或吞吐成为瓶颈时再扩展解析流程 |

选择 pgvector 是为了复用已有 PostgreSQL，避免再部署检索服务；其默认支持精确近邻查询，近似索引可以按需添加。精确近邻只保证按所选距离取近邻，不保证语义答案正确。[官方说明](https://github.com/pgvector/pgvector#indexing)

**保留插件边界，避免提前写框架。** 检索实现放在现有知识插件中，业务工具只依赖现有输入输出契约；首版只有一种存储实现，不预写 Milvus 适配器、双写、路由工厂或迁移平台。未来替换时利用文档 ID、版本和原文重建索引，再评测和切换。

**不能简化掉的部分：** 产品与权限约束、版本／来源、必要操作条件、图像真实读取和可解释的缺知识处理。embedding 不可用时继续查精确条目、按已知产品读取受权原文；数据库不可用时不伪造证据或批准操作。资料撤回在数据库内生效，已进入任务的派生上下文仍按第五、六步处理失效。

## 6. 首版验收

固定资料、模型与上下文预算，对照“仅精确／关键词查询”和“加入语义检索”的方案。用人工标注的产品、证据及必要前提检查：同名消歧、错型号／版本、中文口语、故障码、跨页表格、模糊图片、无知识和资料撤回。

记录证据 Recall@K、错范围召回率、前提完整率、引用支持率、无依据操作率及查询延迟／成本。直接提供正确证据作为对照，区分检索与生成错误。未达到目标时先修数据和切分，再根据上表决定要不要加组件；实验与测试代码不计产品代码预算。

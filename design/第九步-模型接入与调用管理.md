# 第九步：模型接入与调用管理

**状态（2026-09-14）：已并入首版设计基线；已核对官方能力与参考实现，未调用付费 API 或完成模型评测。** 默认按“托管 API 跑生成模型、小型 embedding 本地运行”设计。模型只是提供决策或观察，工具权限、任务状态与业务执行仍由前几步的 Harness 管理。

## 1. 为什么需要这一层

同一任务可能调用模型规划、读故障图片、压缩历史和提取记忆。若每处自行发请求，会出现重试叠加、后台费用漏记、工具参数未收齐就执行，以及换模型后消息格式不兼容等问题。

**首版：成熟 SDK＋一个生成适配器＋一个 embedding 实现。** 调用管理复用既有运行时与后台任务，不建模型网关。按用途约束请求，比给每种用途单独部署一个模型更容易调试。

## 2. 模型怎么分工

| 用途 | 首版候选与调用方式 | 理由及边界 |
|---|---|---|
| 主 Agent | 百炼 `qwen3.5-35b-a3b`，先用非思考模式 | 官方列明支持视觉、工具调用和结构化输出；先建立延迟与任务表现基线，不因为激活参数少就推断部署显存小 |
| 图片观察 | 同一模型，经 `inspect_image` 调用，关闭工具 | 只发送授权图片和观察目的，输出可见事实、可读性及不确定项；复用模型，不继承主 Agent 的业务执行权限 |
| 历史摘要／Memory 候选 | 同一模型，无工具，分别使用第五、六步的输出结构 | 先减少模型数量；历史原文属于数据，候选不能直接覆盖当前状态或写入有效记忆 |
| 向量化 | `Qwen/Qwen3-Embedding-0.6B`，本地 Sentence Transformers | 中文用户表达与外文手册需要跨语言检索；该系列提供多语言和指令感知能力，0.6B 作为资源较小的起点 |

这是候选配置，不是效果结论。[百炼模型能力](https://help.aliyun.com/zh/model-studio/qwen3-5-35b-a3b)与[Qwen 模型卡](https://huggingface.co/Qwen/Qwen3.5-35B-A3B)支撑接入可行性；售后准确度由第八步验证。近期的 [`qwen3.8-27b`](https://help.aliyun.com/en/model-studio/qwen3-8-27b)作为一次离线对照，不在运行中自动切换模型或开启复杂问题路由。

embedding 使用同一权重版本、tokenizer、查询指令和归一化规则生成文档与查询向量，首版保留 1024 维。查询按官方方式附加检索指令，文档输入采用原文及已核对元数据；两者的模板分别固定。检索插件校验向量维度与有限数值。[官方实现与用法](https://github.com/QwenLM/Qwen3-Embedding)

模型或输入模板变化可能改变向量空间，即使维度相同也不能混用。索引记录 embedding 配置版本；变更时用原文重建、评测，再按第七步发布切换，查询向量始终匹配当前索引版本。更换生成模型则无需重建向量。

## 3. 复用 SDK，自己管理调用边界

使用 `openai` Python SDK 的 `AsyncOpenAI` 调百炼兼容接口；只用 Chat Completions 所需能力，不引入 Agents SDK 的循环。SDK 负责 HTTP、连接复用和协议反序列化，我们负责以下小范围转换。[百炼兼容接口](https://help.aliyun.com/zh/model-studio/compatibility-of-openai-with-dashscope)

| 契约 | 最小内容 |
|---|---|
| 请求 | `task_id / step_id / call_id / purpose`、任务版本、模型配置版本、第五步构建的消息、允许的工具、输出约束、剩余预算和截止时间 |
| 完整结果 | 普通文本或工具调用列表、结束原因、实际模型标识、用量、供应商请求 ID；辅助调用另按其 JSON 结构校验 |
| 异常 | 鉴权／配置错误、临时不可用、超时、输出截断、格式错误、用户取消；不把它们伪装成“知识不存在” |

宿主启动时装配受信适配器；`purpose` 决定固定请求配置，不提供任意提示词插件市场。服务商参数只在适配器内映射，例如百炼的 `enable_thinking` 与自部署服务的参数位置可能不同。模型 URL 和密钥来自服务端配置，工具和用户输入不能修改它们。

**“兼容接口”不是能力完全相同。** 接入验收实际检查工具选择、图片、结构化输出、结束标记和 usage；不根据模型名称猜支持，也不在出错后静默删除约束。强制 TODO 按第二步处理：能指定工具就指定，否则只暴露 TODO 并拒绝其他输出。

辅助输出用现有 Python 类型校验能力（Pydantic）验证；供应商支持时启用结构化输出，但仍检查引用和业务条件。主 Agent 的工具调用与辅助 JSON 输出分别请求，不假设同一个接口能同时支持所有格式约束。结构正确不代表观察、摘要或回复在语义上正确。

## 4. 一次调用怎样安全结束

```text
运行时／后台任务 → 校验版本、预留预算 → SDK 请求
                                          ↓
工具执行／发布候选 ← 版本复核、完整校验 ← 汇总结果与用量
```

SDK 可用流式响应接收数据，但**首版缓存模型正文，收齐并校验后再发布**；前端实时显示已有工具事件和固定状态提示。这样无需新增“边生成边判断是不是操作指令”的机制。操作指导仍走已审核步骤卡，自由文本不能代替操作卡；自由文本违规属于必须评测的风险，不声称格式校验能杜绝它。

工具参数残片、结束原因为长度截断、无完整结束状态的响应都不执行；同一响应中先完成整组调用的格式校验，再交第二步按顺序执行。进入等待后剩余调用仍需补齐未执行结果。若已持久化完整决策，恢复时继续处理该决策；否则丢弃残片，重新请求仍占用原任务预算。

每次发布回复、执行工具或写入摘要／Memory 前复核相关任务、产品和来源版本。旧响应不能覆盖新输入。取消请求会关闭本地流并阻止新动作，但不保证供应商停止计费；已发出的业务写入仍按原动作记录对账。

## 5. 重试、预算和成本统一处理

**关闭 SDK 自动重试：`max_retries=0`，由原运行时统一决定。** SDK 默认会重试部分错误，如果外面再重试，实际请求数会多于设计预算。[SDK 重试说明](https://github.com/openai/openai-python#retries)

| 情况 | 首版处理 |
|---|---|
| 连接失败、临时 429／5xx | 同一调用最多额外请求一次，检查剩余预算并尊重 `Retry-After`；等待超出本轮截止时间则保存进度，不在 Worker 内长等 |
| 鉴权失败、模型不存在、不支持参数 | 不重试、不自动换供应商；记录配置错误并给出可恢复的服务状态 |
| 完整输出的参数／JSON 不合法 | 可反馈明确错误纠正一次；这是新模型请求，主 Agent 纠正也算新的决策步，不冒充网络重试 |
| 图片模糊或资料不足 | 返回真实缺项，由主循环澄清；反复调用模型不能补出看不见的事实 |
| 摘要失败、Memory 提取失败 | 摘要按第五步退回文件目录与节选；Memory 保留原事件和待处理状态，不阻断已能继续的客服任务 |

继承每轮 **8 个主决策步、16 次工具调用**；补充起始上限：前台一轮最多 **16 次实际生成请求**（主决策、视觉、摘要及重试合计），单次生成请求总时限 **45 秒**、本轮从认领开始 **180 秒**。这些是待评测的应用上限，SDK 读超时不代替整次调用截止时间。后台每次提取作业最多 2 次实际请求，费用归属原任务，不能凭重新入队无限重置累计预算。任务累计与公网每日额度见[第十二步](第十二步-部署运维与成本控制.md)。

先采用主模型输入上限 16K Token、输出上限 2K Token；辅助摘要／观察输出上限 1K。实际可用输入仍由第五步公式取更小值，图片与工具协议开销必须计入。embedding 文档片段以 1K Token 为起点，计入标题等拼接内容；超限回到切块或上下文选择，禁止 SDK 静默截断。以上参数集中放已有配置，不散落在工具内。

发请求前在 PostgreSQL 原子预留请求次数与 Token 额度，发出后记录 attempt；用量返回后结算。失败但可能已计费的请求保留“估算／未知”，不能计零或直接释放全部预留。前后台共享任务累计额度；离线资料向量化记导入批次成本，在线查询向量化记任务成本。

计费 Token 分类沿供应商语义记录，避免把已含在总量中的缓存／推理 Token 再加一次。价格表注明日期，费用区分估算与账单核对值；本地 embedding 记录耗时与资源成本，不标成零成本。默认不保存原始推理过程，也不把它当 Memory。

## 6. 怎么上线，怎样证明选型合适

默认使用百炼北京地域，部署者从控制台取得匹配地域的 `MODEL_BASE_URL` 与 `MODEL_API_KEY`；模型 ID 和上述限额由配置管理。只需要一个模型服务账号，不需要 OpenAI 账号。密钥仅在后端注入；客户端不直接调用模型。官方文档可访问，实际账号权限、配额及鉴权尚未联调。

FastAPI、现有 Worker、PostgreSQL／pgvector 和 Redis 延续原部署；embedding 在 Worker 启动时加载一次，用受限执行池处理同步推理，不阻塞异步事件循环。文档批量解析／向量化作为离线命令，避免与接待争资源。复用后台任务和现有限流，不增加独立推理网关或调度服务。

这一路线假设托管 API 可用，且小型 embedding 满足目标机器的延迟与内存要求。API 中断时保存任务并展示固定状态，精确资料查询仍可用；embedding 不可用按第七步退回精确查询。性能不足时再比较托管 embedding 或自部署 GPU，不因“0.6B”就承诺 CPU 延迟。10 倍负载先观察供应商限额与本地向量化排队，再决定扩容。

**验收顺序：** 先用固定响应验证截断、重复调用、版本失效、重试上限和用量缺失；再用真实模型验证工具／图片协议。随后用 48 条开发起步场景比较默认模型、思考模式及新模型对照，每次只改一个变量；第八步的 240 条正式集用于重要版本报告。比较完整任务结果、错误动作、图片观察、证据链、延迟和总成本，不用公开榜单替代本项目结果。

生成模型配置切换在安全的轮次边界生效，运行中请求仍绑定旧配置；出问题恢复上一配置，无需改业务数据。embedding 变更保留旧索引直到验收完成。锁定依赖及可获得的模型版本；供应商不提供固定快照时如实记录可复现性限制。

# 第八步：数据准备与评测闭环

**状态（2026-09-14）：已并入首版设计基线，采用 48 条开发起步＋240 条正式评测。** 已检索核对下述官方入口与文章，尚未批量采集、完成附件核验或实现评测。首版采用来源清单、场景文件和一个 Python 评测入口，复用任务事件与模拟业务后端。

## 1. 为什么现在设计

“回复像客服”与“解决售后问题”不是同一个验收标准。产品确认错误、反复推荐已失败步骤、未确认就提交工单，即使措辞友好也应判失败。我们要检查**证据、交互过程和业务结果**，让后续模型、embedding 与提示词选择有共同依据。

服务范围仍是安克全产品；有限样本只决定当前能验证什么，不把未采样产品设成只能转接。产品目录覆盖、可用资料覆盖和评测覆盖分开报告；拿不到全量目录时，不能虚构全公司覆盖率。

## 2. 数据从哪里来

**知识主体采用官方公开资料；自建数据补交互和模拟业务。** 本轮未找到经核验、可直接替代安克产品知识的完整开放数据集；也不假定赛事提供了内部订单、经销商名录或历史工单。

| 知识类型 | 已找到的具体来源示例 | 在项目里怎么用 |
|---|---|---|
| 产品身份与型号 | [Anker 737／A2148 手册入口](https://service.anker.com/article-description/A2148-Anker-737-Charger-GaNPrime-120W-User-Manual)；[eufy 维修型号表](https://service.eufy.com/article-description/eufy-Repair-Application-Instructions) | 提取品牌、显示名、标准型号与地区，进入产品目录；不按营销名或页面推荐列表猜映射 |
| 使用说明及必要前提 | [SOLIX C1000/C1000X／A1761 澳大利亚版指南](https://service.ankersolix.com/article-description/Anker-SOLIX-C1000-C1000X-Portable-Power-Station-USER-GUIDE-A1761-en-AU)；[NEBULA 手册入口](https://www.seenebula.com/eu/downloads) | 保留章节、表格、警告、图示和页码；手册入口需继续核验实际附件，不把附件标题当完整知识 |
| 故障与排障 | [eufy S1 Pro 吸力减弱](https://service.eufy.com/article-description/What-should-I-do-if-my-S1-Pro-s-suction-becomes-weak)；[Liberty 4 NC 重置指导](https://service.soundcore.com/eu/article-description/How-to-Reset-soundcore-Liberty-4-NC) | 建立症状、可能原因、前置条件、步骤和反馈的证据关系；审核后形成操作卡，不能把可能原因当确诊 |
| 软件操作与版本线索 | [NEBULA Capsule Air FAQ](https://service.seenebula.com/article-description/Capsule-Air-FAQ)中的系统更新与设置入口 | 只支持文中明确说明的操作；没有发布说明就不能生成固件故障修复史 |
| 服务政策与升级 | [Anker 美国政策](https://www.anker.com/policies/refund-policy)；[eufy 维修申请说明](https://service.eufy.com/article-description/eufy-Repair-Application-Instructions) | 保存地区、适用型号、渠道条件与所需材料；政策正文供检索，审核后的条件进入既有业务校验 |
| 渠道与安全公告 | [Anker 澳大利亚渠道核验入口](https://www.anker.com/au/verify)；[官方召回公告示例](https://www.anker.com/de/rc2506) | 只有明确可核验的条目才形成结构化记录；核验入口不等于完整名录，型号命中也不能代替批次／序列号核验 |

这些例子是采集种子，不是限定服务产品范围。按各品牌官方目录扩展，记录每个已发现型号的“有目录／有手册／有排障／有政策及地区”覆盖情况；目录不完整时只报告已发现范围。维护者检查适用条件后通过第七步离线流程发布，资料数量与评测题数分别统计。

**采集先保证不串型号。** 只取文章主体和明确关联的附件，去掉导航、推荐列表与页脚；官方支持页也可能同时出现其他产品。HTML 优先，PDF 保留原件及页码，需要时用 Docling；外文正文保留，中文翻译只作可追溯派生视图，型号、数值和条件需核对。用来源 URL、内容哈希、资料版本关联原文与片段；抓取时间不当政策生效时间，缺项标为未知。

**生成的边界：** 可以辅助提取目录字段、翻译、整理有原文依据的步骤，以及生成用户问法、模拟订单／工单／渠道记录。不能生成新的错误码含义、技术参数、固件历史、官方授权关系或保修承诺。模拟业务用现有业务表查询，和真实产品知识区分；经审核的脱敏服务经验仍按第六步管理。

[τ-bench](https://github.com/sierra-research/tau2-bench/tree/main/data)用于交互任务结构参考，[Bitext](https://github.com/bitext/customer-support-llm-chatbot-training-dataset)用于客服表达变体；它们和原欧莱雅数据都不作为安克技术事实。论坛经验首版不直接发布为指导。手册图可用于辅助定位部件；真实故障图片需要自摄或获准使用的样本，合成图只验证流程。

公开可读不等于开放许可。来源清单记录使用条件；不便再分发的原文或图片不随开源仓库发布，只保留允许发布的引用信息与自建样例。缺少适用资料时按既有流程澄清或升级，不用生成内容填成“官方答案”。

## 3. 一条场景记录什么

每条 JSONL 场景包含六组信息；前端演示与评测复用同一场景定义。

| 字段组 | 内容 |
|---|---|
| 身份与初态 | 场景 ID、用户／设备／订单／工单初态、任务与资料版本 |
| 用户可见信息 | 初始消息、授权图片 ID、用户掌握的事实与可反馈的操作结果 |
| 评测专用真值 | 正确产品、支持结论的证据组、必要前提、允许的服务结局；与模型上下文隔离 |
| 过程要求 | 必须先满足的条件、禁止动作；只规定必要顺序，不规定唯一工具调用轨迹 |
| 故障设置 | 在哪个事件后断线、重启或丢回执；使用固定场景时钟与种子 |
| 来源与划分 | 来源链接／哈希、许可记录、真实或合成标记、场景家族、开发／保留集 |

**示例：升级回执丢失。** 模拟后端已经创建工单，客户端尚未收到回执。验收要求恢复后按同一动作 ID 核验、只存在一张工单、证据包仍对应用户确认版本，并显示“未解决、已升级”。它不是设备修复成功案例。

规模调整为 **48 条开发起步场景＋240 条独立正式评测场景**，正式集下列六组各约 40 条；表达改写、图片干扰和故障注入形成单独的鲁棒性测试。按场景家族隔离开发与正式集，同一工单及近似改写不得跨集。派生样本及重复运行不增加独立基础场景数；这些数字是实施目标，不是实测结果或全产品覆盖保证。开发集经常运行，正式集在重要版本完整运行，按失败与覆盖缺口持续补样本。

1. 同名／近似型号消歧，以及中途更正产品。
2. 清晰、模糊、矛盾的图片线索；紧迫情绪下仍需必要澄清。
3. 单跳、多跳、版本冲突、资料缺失与撤回。
4. 已试无效、不便执行、确认恢复与跨会话接续。
5. 内部订单缺失、渠道不明、凭证不足与受控升级。
6. 长上下文落盘读回、Memory 更正、越权尝试、重复事件和提交后丢回执。

保留集对开发期提示词、Skill 示例和经验提炼隔离；检索库允许含答题所需的官方手册，但不能含测试题、标准答案或评测运行产生的记忆。每次运行创建独立测试用户和初态，结束后清理；不让上一轮记忆提高下一轮分数。

## 4. 怎样跑通评测

```text
场景初态 → 现有 Harness → 任务事件＋数据库结果＋引用记录
               ↕                         ↓
       模拟业务后端／用户反馈       确定性断言＋人工复核 → 报告
```

**工程回归与智能效果分开。** 重复提交、权限、重启等回归可以注入固定模型输出，验证代码约束；这类通过率不能算模型能力。端到端效果必须调用待测模型，并走真实上下文、检索和工具校验路径。

首版不开发通用用户模拟 Agent：卡片选择与已定义结果用固定反馈；开放式澄清由测试者依据隐藏用户事实作答，不能透露答案或迁就错误问题。自动运行碰到未定义分支标记“需人工完成”，不能静默跳过并计成功。正式报告完成所有场景后再统计。

每次记录代码／资料／场景版本、模型和 embedding 标识、提示词哈希、推理参数、任务预算及种子；固定种子不代表远程模型完全确定。保留集每条独立运行 3 次，报告平均成功率及三次全部通过的场景占比，不取最好一次。跨运行失败修复后发布新评测版本，保留旧结果。

## 5. 什么算成功

| 维度 | 主要判据 |
|---|---|
| 产品与图片 | 产品身份和版本绑定正确；图片观察与人工标注可见事实一致；看不清时保留不确定性 |
| RAG | 必要证据召回、适用范围正确、操作前提完整；多跳统计“全部必要证据组均命中”的比例，允许等价证据 |
| 服务结果 | 分开统计确认恢复、有效升级、正确待补信息；这些结果不能合并称为修复率 |
| Harness 约束 | 无越权、无未确认写入、无重复工单；旧产品卡片失效，更正后的记忆不再误导后续任务 |
| 共情与效率 | 人工按“承接具体诉求／不重复已知问题／下一步清楚且可执行”逐项 0 或 1 分；报告模型与工具调用、输入输出 Token、首个有效响应与整轮处理耗时 |

总场景通过必须同时满足业务结局、必要过程和禁止动作要求。对所有合法结局都预先标注判据：可解决场景无理由升级不算成功；待补信息只是该检查点正确，不能说全任务完成。用户等待时间与系统处理耗时分开，重试和后台模型调用也计成本。

工程回归中的禁止动作要求全部通过，有一次失败就修复后重跑；零次失败只代表当前样本未观察到。模型效果先报告基线及逐类结果，不凭空许诺 95% 准确率。共情与引用支持先人工核对；如以后增加模型裁判，只作辅助，不能覆盖确定性违规结果。

**只做有解释力的对照：** 固定主模型与资料，比较精确查询、精确＋语义、再加按需多跳；单跳样本同时检查多余检索。另给正确证据作诊断对照，区分“没找到”与“不会用”。Memory 在跨会话组比较启用前后；安全约束始终启用。评测代码不计入产品代码预算。

| [RAGChecker，NeurIPS 2024 Datasets and Benchmarks 轨道](https://proceedings.neurips.cc/paper_files/paper/2024/hash/27245589131d17368cccdfa990cbf16e-Abstract-Datasets_and_Benchmarks_Track.html) | 借鉴拆分检索与生成错误、逐条检查断言证据；先人工标注小集合，不部署独立裁判服务 |

来源核对于 2026-09-13。τ-bench 仓库当前已介绍 τ³ 扩展，本设计主要借鉴 τ² 的交互思想，使用数据时固定版本；ToolSandbox 论文属于 Findings of NAACL 2025，不标为 CCF-A 主会论文。上述机制尚未在本项目验证收益。

**ponytail 结论：** 实现时只增加 `data/sources.jsonl` 来源清单、`evals/cases.jsonl` 场景和 `evals/run.py` 入口，JSON／Markdown 报告直接落本地；图片及原件走已有材料存储。零新增服务、零评测专用账号，复用待测模型配置；不做标注平台、自动生成千条样本或榜单网站。最脆弱的前提是模拟反馈能代表真实排障，因此实物人工演示单列，模拟通过率不能外推真实修复率。

模型接入、前后端和部署已在第九至十二步补齐；按[第十三步](第十三步-实施路线与交付验收.md)开始建设数据与代码，用开发集检验模型与资源配置。

# 第四步：权限与安全边界

**状态：已按安克全产品售后场景修订（2026-09-12）。** 保留资源级授权、数据库最小权限与文件范围限制；11 个工具共用检查，补充图片证据、排障操作和渠道核验边界。下一步见 [上下文管理](第五步-上下文管理.md)。

## 1. 先定义允许范围

防范三类问题：模型被聊天／检索内容诱导越权、用户伪造资源 ID、实现错误造成跨用户访问或误写。首版只加载随项目发布并审查的插件；不承诺在同一 Python 进程内安全运行恶意插件。

**每次访问都核对：服务端会话主体 → 当前任务 → 资源可见性 → 允许动作 → 当前条件。** 产品目录和公开手册可供访客查询；私人订单、凭证和工单须验证身份与归属。访客上传只绑定其隔离会话，不因图片含订单号而获得订单访问权。人工账号也只读授权任务。

| 能力 | 允许范围 | 明确拒绝 |
|---|---|---|
| 订单／售后查询 | 当前用户拥有的候选订单；选定后按任务关联读取详情 | 猜中别人的订单号；用旧会话读另一用户任务 |
| 产品／技术／政策检索 | 公开产品目录；已确认产品、地区、渠道适用资料 | 强选同名产品；绕过可见性过滤；把其他客户原始工单当知识返回 |
| 草案／待办／TODO | 本任务内相应记录；更新须匹配版本 | 写批准标志、改业务回执或自行改变用户目标 |
| 图片与质保核验 | 当前任务材料；名录、政策及已核验购买事实 | OCR 结果冒充验真；订单缺失或经销商无匹配直接判无保修 |
| 排障指导 | 当前产品可适用、已审核且允许用户执行的步骤 | 自编物理操作、跨型号套用、越过步骤安全限制 |
| 工单提交 | 运行时执行已确认且仍有效的升级草案 | 模型直接执行；确认后更改接收方、产品或材料范围 |
| Skill／材料文件 | 已安装 Skill；授权材料 ID 对应的文件 | 任意路径、远程 Skill、自行写代码或配置 |

统一执行器负责参数与资源检查，数据库和文件层再限制实际读写。确认接口还核对草案版本与登录身份；使用 Cookie 会话时加 CSRF 防护。检查失败返回可解释的错误码，日志记录拒绝原因；面向用户的响应不泄露他人资源是否存在。

## 2. 数据库：既限定操作，也限定数据

采用固定仓储方法和参数化查询，例如 `orders.get_owned(order_id, principal)`。表名、列名、SQL 片段和权限上下文都不由模型提供。

| 数据库角色 | 权限用途 |
|---|---|
| 业务读取角色 | 仅读取必要产品、订单、经销商、政策和售后字段，不得写业务表 |
| 任务工作角色 | 保存本任务 TODO、步骤卡、观察与草案；不得写用户确认／反馈、实际回执及业务表 |
| 运行时执行角色 | 由受信确认／执行路径写确认记录、指定业务字段及回执；无建表、删表等管理权限 |
| 迁移角色 | 仅部署迁移时使用，凭据不注入在线进程 |

角色通过表／列授权落实，不是四个微服务。界面事件路径写产品确认、步骤反馈与审批，模型工具只存候选和观察；不能给所有工具共用管理员连接。知识和经销商名录由受信导入路径更新，在线模型无权改名单或规则。

客户相关表增加 PostgreSQL **RLS（行级安全）**，作为遗漏查询过滤条件时的第二道防线：读用 `USING`，写用 `WITH CHECK`；在线角色不是 owner、superuser 或 `BYPASSRLS`，也不能切换到高权限角色。[RLS 官方文档][rls]

连接池每个事务通过 [`SET LOCAL`][set-local] 设置服务端验证过的身份范围，不用会话级 `SET` 留存用户身份；提交／回滚后局部设置失效，缺少上下文默认拒绝。任务和材料同时核对消费者归属，不能只按商家隔离。RLS 上下文不是认证机制，也不能抵挡持有凭据且能执行任意 SQL 的恶意宿主代码。

Redis 按服务设置命令／键权限，已启用缓存的键包含授权范围与版本，不把跨用户结果混用。首版 pgvector 知识表沿用 PostgreSQL 读写权限：在线检索只读，知识更新走受信导入路径；过滤由服务端构造，返回前核对来源可见性。后续若引入 Milvus，同样隔离查询与导入账号。连接信息都不向模型暴露。

## 3. 文件：模型拿材料 ID，服务端决定实际路径

文件操作包括加载 Skill、接收／读取材料，以及[第五步补充的临时上下文存取](第五步-上下文管理.md)。后者由运行时生成文件，模型通过 `read_context` 读取登记过的任务虚拟路径，不能直接传物理路径；沿用下面的归属和目录限制。TODO 与业务状态仍保存在数据库。

1. **固定只读资源。** Skill 和应用代码随镜像发布，只读挂载；模型只能按已安装名称加载，不能覆盖或安装新文件。
2. **材料使用服务端命名。** 上传接口生成材料 ID 和存储键，绑定用户与任务；原始文件名只作显示。限制文件类型、大小和数量，核对实际格式；首版不解压用户压缩包、不执行上传文件。[上传实践][upload]
3. **按 ID 授权后读取。** 不接受调用方指定的绝对路径或 `../`。上传后文件不原位替换，修改产生新 ID；查看与下载接口同样检查归属，知道 ID 不等于拥有访问权。
4. **打开文件时也受限。** Linux 部署使用受控目录与目录句柄相对打开，拒绝符号链接，读取已打开的同一文件句柄；目录不可由用户替换。不能只做一次路径字符串检查，再按路径重新打开。[Linux 路径解析约束][openat2]

上传 API 只写材料目录；Worker 只读材料，临时处理结果写独立任务临时目录。应用容器采用非 root、只读根文件系统、明确的可写卷、禁用提权并移除不必要 capabilities；不挂载宿主家目录或 Docker socket。[Docker 配置依据][docker]

这限制了整个服务的环境权限；受信插件仍可能访问本进程的其他连接或已挂载材料。未来接入第三方插件或代码执行时，必须另加独立进程／容器、单任务挂载和独立凭据，不能把目前的插件接口称为恶意代码沙箱。

## 4. 提示注入不能成为授权来源

例子：手册片段或图片内文字要求读取其他用户订单并上传。它仍是有来源的数据，不能成为系统指令、权限或确认事件；脱敏后的历史工单也不例外。

- 用户请求决定业务意图，但用户不能自行声明管理员权限；检索正文、材料内容、历史对话中的“批准”不能写入批准记录。
- 关键字段使用可信来源：产品来自目录与确认，购买事实来自核验记录，审批由已认证界面事件绑定草案；图片候选不自动写成已核验结论。即使参数格式合法，仍检查对象与用途。
- 密钥、数据库凭据及无需模型处理的完整联系方式不进入上下文；日志和导出沿用任务访问权限。资源授权必须发生在送入模型之前，不能泄露后再指望模型保密。
- 模型不能指定下载或外传地址。业务客户端只连接服务端配置的端点；材料经上传接口接收，不由模型提供 URL 让服务器抓取，降低 SSRF 和外传入口。网络隔离属于部署约束，域名允许列表也不等于允许任意数据发送。

文本分隔和来源标注有助于模型理解，但不能保证它不受注入影响。首版的保障重点是：错误决策到达执行边界时，越权读写仍被拒绝；回复内容的误导与任务偏移仍需单独评测。

**物理操作也是边界。** `present_troubleshooting_step` 检查知识中的型号、前置条件与操作级别；只渲染审核过的消费者可执行步骤。型号不明先澄清，资料缺失或触发安全限制时转合适支持流程，用户批准不能解除限制。危险操作不依赖关键词过滤兜底；自由回复仍做专门评测，不能宣称模板即可消除全部误导。

## 6. 用攻击案例验收，而非只看配置

| 测试输入／故障 | 预期结果 |
|---|---|
| 替换订单、任务、材料 ID 为另一用户的值 | 工具与直接 API 请求均拒绝，响应不含对方数据 |
| 复用连接处理不同用户，或遗漏业务查询过滤 | RLS 拦截跨用户结果；无身份上下文默认拒绝 |
| 文件名含路径穿越、材料指向符号链接、旧 ID 被重放 | 只能读取授权的固定文件，不能越出目录 |
| 检索结果诱导写数据库、读配置或访问外部网址 | 不获得工具、资源或网络权限，记录拒绝 |
| 草案确认后改产品／接收方、重复提交或权限不足 | 旧确认不可复用，不重复建工单；权限失败不能自动升权 |
| 错型号步骤、图片伪造授权、无订单的经销商购买 | 拒绝不适用操作／伪造授权；购买信息不足进入核验，不无依据拒保 |

同时测正常任务通过率与误拒绝率，避免靠全部拒绝得到好看的安全结果。以上是待实现的验收要求，评测代码不受产品行数预算限制。

**本轮建议：首版落实资源级授权、RLS 与文件范围限制；继续只支持受信插件。** 在这一范围内先把边界测清楚，再考虑是否需要接入不受信代码。

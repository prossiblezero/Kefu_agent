# 第十一步：前端交互与人工接续

**状态（2026-09-14）：首版实施设计，尚未实现。** 页面必须让用户知道“你理解了什么、正在做什么、我下一步做什么”，让人工客服直接接续已发生的服务过程。

## 1. 技术与页面范围

采用 **React＋TypeScript＋Vite，原生 fetch／EventSource，CSS Modules**。前端只呈现后端事实和发送第十步的事件；不在浏览器重写 Agent 状态机。首版用 useReducer 管理一个任务页的快照、事件和请求状态，不引入 Redux、独立 Node 后端或 Next.js 服务端渲染。

只有三个工作入口：`/tasks/:id` 消费者服务页、`/me/memories` 记忆管理、`/staff/tasks/:id` 人工接续页。任务列表与登录作为导航和入口，型号管理、资料审核及账号分配暂用维护 CLI，不增加后台管理网站。

```text
消费者桌面页
┌──────────────┬───────────────────────────┬─────────────────┐
│ 我的服务记录  │ 对话与当前操作卡            │ 当前产品与进度    │
│ 未解决／已完成│ 用户消息、完整回复、原图预览 │ 已确认／待确认    │
│              │ [一步操作＋必要警告]        │ 已试步骤与结果    │
│              │ [无变化] [无法执行] [恢复]  │ 资料依据／工单    │
│              │ 输入、上传、发送／停止      │                 │
└──────────────┴───────────────────────────┴─────────────────┘
移动端：同一条服务流，任务列表和进度改为展开区域，操作卡保持可见。
```

这是布局约束，不是最终视觉稿。默认浅色、高对比、单一蓝色操作强调色；状态同时用文字表达，避免只靠红绿。重点位置留给当前动作，不做情绪仪表盘、Agent 思维链或技术组件展示。

## 2. 每张卡片必须形成闭环

| 交互 | 用户看到什么 | 提交与后续行为 |
|---|---|---|
| 产品确认 | 名称、标准型号、能区分候选的图片／描述，以及“都不是” | 选择候选 ID＋卡片版本；确认后绑定产品。都不是则补充线索，不强选第一项 |
| 故障图／凭证 | 上传状态、本人原图预览、用途说明；读不清的字段明确标注 | 上传完成取得材料 ID 后才随消息提交，失败可重试上传；不将上传成功显示为票据核验成功 |
| 排障步骤 | 本次一步、适用产品、前提、警告与预期现象，可展开依据 | “已操作／无变化／无法执行／已恢复”发送步骤实例和产品版本；成功后显示回执，等待下一步 |
| 升级草案 | 未解决问题、已试步骤、附带材料、接收方和待核验项 | 用户看完整内容后确认；重复点击沿用幂等 ID。内容变更必须形成新版本重新确认 |
| 工单接续 | 实际回执、提交中／核验中／已受理／待补充／已处理 | 已受理显示“未解决、已升级”；人工仅提供建议时等待用户反馈，不自动显示修复成功 |
| 记忆管理 | 有来源、时间、设备范围的有效记忆 | 更正或遗忘后等待服务器确认，刷新相关摘要；不能只在页面隐藏旧内容 |

完整回复到达前，只显示“已收到”“正在核对产品资料”等来自程序事件的进度，不显示假百分比，也不把模型 token 流当业务进度。首次接收确认目标为 1 秒内，模型生成时间另测。卡片正文来自服务端审核对象，前端不拼接额外物理操作建议。

## 3. 断线、冲突与交互细节

首次加载取快照及游标，再接 SSE；所有服务器事件以序号去重，gap 通过补读解决。状态由服务器确认后改变，本地只临时显示“发送中”。消息 client_event_id 在首次点击时生成，网络重试沿用；失败时保留编辑框内容，不能悄悄重复发出。

多标签页或中途换产品导致旧卡失效时，显示“信息已更新，请查看当前步骤”，刷新快照并禁用旧按钮。产品更正可以从进度区发起，保留历史设备记录。SSE 会话失效则重新登录；断线只停止订阅，显式“停止”才发取消事件，已发出工单显示仍在核验。

“继续处理”只恢复允许恢复的任务，不重置任务累计预算或待核验操作。配额用尽时解释暂停原因；工单核验优先，不能借继续按钮重复提交。超过一轮时间仍未完成时保留进度，不让用户从头描述。

输入框默认保留多行编辑，发送按钮明确；键盘可访问所有卡片，焦点在卡片更新后保持合理位置。屏幕阅读器只朗读新增状态，减少重复播报。消息显示用户所在地时间，但事件保存 UTC；“明天”按发送时区绑定具体日期。

首版上传允许 JPEG／PNG／WebP，每张不超过 10 MiB、解码不超过 2000 万像素，每条消息最多 3 张、每任务总计 50 MiB；后端核验真实格式与归属。SVG、压缩包及用户 PDF 暂不进入上传入口；管理员手册导入另走离线流程。显示缩略图但授权原图仍可读，不能用缩略图替代故障小字核验。

模型文本默认作为普通文本渲染，段落换行保留；需要链接时用服务端给出的证据对象生成。不开任意 HTML、脚本或远程图片渲染，避免把恶意资料带进页面。证据抽屉显示标题、型号、地区、版本、相关片段和授权原件入口。

## 4. 人工怎样接住任务

人工页左侧为已分配任务列表，中间是同一条时间线，右侧为产品与购买信息、已试步骤及反馈、原图／条款、未解决问题和草案／回执。优先级显示来自用户的紧迫事实和等待时长，不展示模型臆测的性格标签。

人工可请求补资料、记录处理进展、提交核验结果，或把新指导交给消费者继续执行；必须带操作者、时间与依据。人工建议不伪装成用户操作。确有已核验修复结果时按第二步完成规则收束；无法证明恢复则保持等待，消费者后续反馈可重新打开任务。

人工与消费者可见信息分别投影：工作人员的内部备注不进入消费者 SSE，外发进展在提交前有明确预览。首版不接邮件、短信、电话或真正安克客服系统；页面与工单回执清楚标记模拟业务环境。

## 5. 验收与参考取舍

用同一组浏览器流程验证桌面和窄屏：图片未上传完不能误发送；确认失败不显示成功；刷新增量不重复；旧卡不可提交；人工只看被分配任务；遗忘后刷新与历史重连不显示被禁用内容。Playwright 覆盖这些真实交互，简单样式不逐项写测试。

借鉴 [assistant-ui](https://github.com/assistant-ui/assistant-ui) 将消息与工具交互呈现分开的思路，首版用少量 React 组件承接自己的持久事件，不安装一套聊天运行时；状态归并复用 [React reducer](https://react.dev/learn/extracting-state-logic-into-a-reducer)，单向事件推送按 [SSE 标准](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)，构建采用 [Vite](https://vite.dev/guide/)。来源核对于 2026-09-14。

ponytail：对话、卡片、证据抽屉、进度与人工接续就够了。这里最容易失败的是页面先显示成功、后端却未成功；所有关键状态都以持久回执为准，界面动画不能改变它。

# 第三步：工具与 Skill

**状态：已按安克全产品售后场景修订（2026-09-12）。** 共 11 个模型工具、3 份通用 Skill；沿用强制 TODO 与受限上下文读取。这里是实现设计，尚未编写接口代码。下一步见 [权限与安全边界](第四步-权限与安全边界.md)。

## 1. 能力按服务职责组织，产品差异由资料表达

Tool 提供一个有输入输出契约的操作；Skill 指导如何组合操作；知识库提供型号适用的技术事实与政策；Plugin 负责装配能力。全产品共用这些职责，不按每个产品创建 Agent、工具或 Skill。

情绪与紧迫性从用户表达中理解，影响追问数量、解释方式和升级优先级；首版不增加独立情绪 Agent。不能凭“用户很生气”跳过身份、质保与执行检查。

## 2. 11 个工具及边界

身份与当前任务由服务端注入；模型不能传权限、批准标志或任意存储路径。

| 工具 | 主要输入 → 输出 | 边界与选型理由 |
|---|---|---|
| `resolve_product` | 名称／型号线索、证据引用 → 产品候选、差异与待确认项 | 跨全产品目录查找；同名不强选。产品通过用户确认卡或已核验记录绑定到任务 |
| `inspect_image` | 材料 ID、观察目的 → 可见文字／部件、模糊项与观察引用 | 用视觉模型读故障图或凭证；观察不等于故障确诊、票据验真或所有权证明 |
| `search_knowledge` | 问题、技术／政策类型 → 适用条款、排障步骤 ID、版本与来源 | 产品、地区和渠道过滤由已确认任务信息约束；缺少范围先澄清。技术知识与政策共用检索接口 |
| `lookup_purchase` | 订单线索／凭证引用 → 自有订单匹配、购买声明与缺项 | 合并订单定位与详情读取，结果分页；内部查无订单进入凭证核验，不返回“无质保” |
| `check_warranty` | 已绑定产品、购买记录／凭证引用 → 适用／不适用／信息不足及依据 | 后端核对经销商名录、购买时间和适用政策；读不清、名录无匹配或规则缺失均不能冒充确定结论 |
| `get_service_history` | 可选关联工单 ID → 当前任务／该用户该产品的工单与步骤记录 | 避免重复排障；跨客户案例只通过脱敏、已审查的知识库检索 |
| `present_troubleshooting_step` | 已检索步骤 ID、前置条件证据 → 版本化操作卡及预期反馈 | 校验产品、适用条件和允许操作；正文取自审核过的步骤，通常一次呈现一步并等待反馈 |
| `propose_escalation` | 原因、证据引用 → 升级草案、缺项或确认摘要 | 自动装入已确认产品、已试步骤、结果和未解决问题；只存草案，不直接提交外部工单 |
| `load_skill` | 已安装名称 → 指导正文与版本 | 按需加载通用流程，不读取任意路径或安装远程代码 |
| `todo` | update／review、预期版本、条目 → 当前计划和复核记录 | 保留目标与进度；不能改产品确认、质保结论或业务回执 |
| `read_context` | 任务虚拟路径、游标、可选关键词 → 限长片段与来源 | 读回外置上下文；文件写入与回收由运行时管理，详见第五步 |

前六个是查询／观察工具；第七个保存当前操作卡，第八个保存升级草案，最后三个管理指导、计划与上下文。工具统一返回 `status / data / evidence_refs / error`，包含适用范围、观测时间和必要版本；业务缺项与接口故障分开。

## 3. 哪些动作由程序掌握

**批准升级、提交工单、对账、保存界面反馈和结束任务**属于运行时。确认绑定草案内容及版本；程序重新检查归属、必要材料和接收方后提交。外部接口未接入时使用明确标注的模拟后端，不宣称工单已到达安克真实客服。

操作卡的“已操作／无变化／无法执行／已恢复”是用户反馈，绑定步骤实例与产品版本，不能由模型自填。“已操作”不代表恢复；自由文本反馈保留原文，需要结束任务时通过绑定当前步骤的确认卡核对，不能从“谢谢”推断成功。普通指导无需升级审批，仍需校验适用性与安全条件。

图片材料由前端上传，服务端分配 ID。清晰度不足则请求补拍或让用户读出关键文字；视觉调用失败时可继续文本澄清，不能编造看图结果。确认产品变化后，旧步骤和受影响草案失效；历史反馈保留原产品归属。

经销商凭证即使不能自动核验，也允许进入人工审查；检索相似案例不能直接替代当前产品手册。维修、换货、退款等后续诉求记录进升级材料，首版实际业务写入聚焦工单提交和接续。

### TODO：保留已讨论的强制机制

- **先计划：** 初次进入模型循环先 `todo(update)`，通常 3～5 项、最多一项进行中；条目有稳定 ID、状态与证据引用。
- **定期复核：** 累计 3 个模型决策步未成功调用 TODO，下一请求强制只允许 TODO，跨用户轮次累计；图片观察和上下文读取所在决策步也计算。
- **成功才清零：** `review` 可以不改计划；须版本匹配且明确复核。无计划不能只 review，参数错误或口头提及不算。
- **不改事实：** 目标或产品确认变化后重新规划；勾选计划不等于用户执行了步骤或问题已解决。任务快照持久保存版本与计数。
- **受预算约束：** 适配器支持时指定 `tool_choice`，否则只暴露 TODO 并由执行器拒绝其他输出。最多一次纠正；规划计成本，不唤醒等待任务，不阻塞固定确认／对账。

## 4. 三份共享 Skill

| Skill | 触发场景 | 核心指导 |
|---|---|---|
| `guided-troubleshooting` | 描述含糊、故障图片、需要排障 | 回应具体困扰；消歧；查技术依据；呈现一步；接收反馈后调整；避免重复已失败操作 |
| `purchase-and-warranty` | 订单缺失、经销商购买、质保询问 | 收集最少必要凭证；核对渠道名录与适用政策；区分确定结论和待人工核验 |
| `escalation-and-followup` | 无法自行恢复、需要专员、已有工单 | 汇总接续材料；解释下一步；确认后提交；跟踪回执，区分受理和解决 |

Skill 保存通用方法；具体型号步骤、风险等级、保修期限、经销商名单从知识与业务记录读取。三份使用基础 `SKILL.md` 格式，正文按需加载，首版不带脚本；不另写每种产品专属长提示词。[加载机制][skills]、[格式依据][spec]

## 5. 串起一个服务过程

> “我的 S1 Pro 不吸了，明天要用！”＋故障图

先制定计划，识别紧迫性；产品目录与图片观察提供候选，让用户确认具体产品。检索适用手册，呈现可执行的一步并等待用户反馈；失败后换有依据的下一步，不能机械重试。

需要售后时查询购买记录；查不到转凭证／经销商核验，未知保修结论作为待办信息保留。无法排除故障则生成包含原图引用、已试步骤和结果的升级草案；用户确认后程序提交，展示实际回执。模型根据需要选工具，以上不是必须逐项走完的固定脚本。

消费者页面承载对话、图片上传、产品确认、操作反馈与升级进度；人工接续页展示同一任务的证据和未解决事项。点击确认、反馈或发送均有独立事件，不能用界面展示代替实际执行。

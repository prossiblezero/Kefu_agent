# 第十二步：部署运维与成本控制

**状态（2026-09-14）：首版单机部署设计，尚未购买资源或上线。** 目标是能从干净环境运行、能定位失败、能备份恢复；部署设计不等于承诺生产 SLA。

## 1. 最小部署拓扑

```text
浏览器 ─HTTPS→ Caddy（静态前端、反向代理） → FastAPI
                                               ↓
                     PostgreSQL＋pgvector ← API／Worker → 托管模型 API
                                               ↕
                                             Redis
Worker：任务循环、恢复、后台提炼；本地加载小型 embedding
持久卷：数据库、原始材料、任务临时上下文、模型权重、HTTPS 证书
```

Compose 常驻 **5 个容器：Caddy、API、Worker、PostgreSQL、Redis**；API 和 Worker 用同一 Python 工程、不同启动入口。前端编译后是静态文件，没有独立 Node 服务。迁移和知识导入是一次性命令，Docling／OCR 依赖在导入镜像中，不装进接待运行镜像。

默认 Linux 部署，Windows 开发通过 WSL2／Docker 运行相同文件边界。Python 3.12、PostgreSQL 17＋pgvector、Redis 7.4、Node 22 LTS 作为首轮兼容基线；实现时锁定通过检查的受支持补丁版本与镜像 digest，不用浮动 latest。Redis 7.4 按[上游许可](https://redis.io/legal/licenses/)保留归属及使用说明；Node 支持期以[官方发布表](https://nodejs.org/en/about/previous-releases)核对。

默认托管生成 API，首轮测量机器取 4 vCPU／16 GiB 内存、100 GiB SSD，无 GPU；这是测试起点，不是已证明的容量或最低配置。模型权重从官方仓库下载并固定 revision，可在可联网环境准备后挂载；运行时不自动下载任意模型。账号需求为模型服务账号、部署服务器及域名管理权限，均由部署者配置，不在文档中索取密钥。

## 2. 上线边界与配置

仅 Caddy 暴露 80／443；数据库、Redis 和 API 端口不公开映射。公网同域部署，开发环境用 Vite 代理避免放开跨域。Caddy 自动 HTTPS 需要域名解析及证书挑战可达；没有域名时只提供本地开发访问，不把无 TLS 的测试环境标为公网完成。

应用容器非 root、只读根文件系统、关闭提权、移除非必要 capabilities；API 可写上传卷，Worker 只读原始材料、可写任务临时卷。托管端点只由配置决定，按最少必要数据发送；不挂载 Docker socket 或宿主用户目录。具体资源级授权仍遵守第四步，容器不是每个插件的独立沙箱。

配置集中到已有 settings：模型端点／密钥、三类在线数据库 DSN、Redis URL、文件根目录、模型版本和预算。迁移凭据只给一次性迁移容器，导入凭据只给导入任务；不注入浏览器或普通工具。知识与账号创建走维护命令；真实生产接口必须替换模拟后端并重新验收，不能只改页面标签。

使用 healthcheck 和 Compose 依赖顺序等待数据库可用；执行迁移成功后启动 API／Worker。服务内部仍处理短暂断连，不能把“启动时健康”当作运行中永远可用。升级先停止新接待、等待在途轮次到安全边界并核对未知动作，再换镜像，防止新旧 Worker 同时派发同一业务写入。

## 3. 首版预算和可观测性

继承第九步的单轮限制，任务累计生成 Token 初始限额 **100 万**，包含失败估算与后台调用；达到上限保留任务，由维护者显式调整额度并记审计，消费者“继续”不会重置。公网演示再设共享每日生成 Token 额度 **50 万**（按 UTC 日），在 PostgreSQL 原子预留，耗尽时停止新模型请求但不阻断已发出动作对账。

Redis 原子计数用于会话／IP 登录与消息限流：登录同来源每分钟 5 次、普通消息每主体每分钟 10 次；拒绝不写业务事件。Redis 故障时关键写入入口采用本进程同限额保守限制，服务仍保持单 API 实例，预算硬上限由 PostgreSQL 兜底。Worker 并发和 embedding 并发按第十步固定起点，不以加大并发解决供应商限流。

不搭独立监控集群。结构化日志关联 `request_id/task_id/step_id/call_id/operation_id`；记录阶段、耗时、错误码、状态变化与 Token，不记录密钥、凭证正文、原图或原始推理。管理员通过只读诊断命令查看：待办最长等待、失败调用、未决动作、模型耗时、Token、资料覆盖及清理积压；诊断导出同样脱敏。

`/health/live` 检查进程；`/health/ready` 检查数据库与 schema 版本。Redis／模型故障显示能力降级，不因第三方中断反复重启进程；日志告警按阈值输出，不集成外发通知服务。初始目标：接收持久回执 P95 小于 1 秒、Redis 丢唤醒后 10 秒内被补扫发现；完整模型轮次、语义检索延迟先测量再报告，不写虚构 SLA。

## 4. 备份、删除和故障恢复

演示环境原始会话、材料、模拟工单默认保留到任务终态后 30 天；未终结任务不按年龄清理。临时上下文在终态且无在途调用／未决动作后立即进入回收，周期补扫。明确偏好保留至更正、遗忘或账号删除；删除记忆时保留最小排除记录，避免重新提炼，不保留已删除的内容正文。

每天低峰进入维护窗口，暂停写入并等待在途处理结束；以同一备份批次导出 PostgreSQL 和原始材料／必要任务文件，记录哈希及应用、schema、知识版本，再恢复接待。备份加密保存到独立主机或受控外部存储，保留 7 份；只存同机卷不算灾备。知识原件许可限制继续适用。

恢复时先在隔离环境校验数据库和文件引用，保持 Worker 停止；合并独立保存的删除／撤回清单、重新核验未决 operation_id 后再开放任务。删除清单与隐私变更同步到受控备份位置，未同步或清单缺失时禁止直接恢复对外服务，避免旧备份复活已遗忘内容。此流程属于小规模演示恢复，不声称拥有连续时间点恢复能力。

数据库不可用时停止授权读取与写入，保留客户端未发送草稿，不靠 Redis 重建事实；文件丢失可按第五步重建临时副本，原件缺失如实报告。回滚应用保留上一个镜像，schema 首版只做向后兼容的添加；破坏性迁移另需备份与恢复演练，不能自动 downgrade 删除数据。

## 5. 发布验收与参考

上线前在空白环境完成：锁定依赖安装、建库迁移、导入许可允许的样例、创建随机密码账号、运行关键集成测试和浏览器闭环；再演练停止 Worker、丢 Redis 通知、API 故障、备份恢复及旧资料撤回。只有真实联网模型测试通过才标“在线模型可用”，固定响应演示必须明显标注。

采用 [Docker Compose 单机生产部署](https://docs.docker.com/compose/how-tos/production/)与[启动健康检查](https://docs.docker.com/compose/how-tos/startup-order/)、[Caddy 自动 HTTPS](https://caddyserver.com/docs/automatic-https)、[PostgreSQL 备份恢复](https://www.postgresql.org/docs/17/backup-dump.html)的现有能力，不自写证书或备份格式。来源核对于 2026-09-14。

ponytail：现有组件加一个入口代理就能上线；暂不增加 Kubernetes、对象存储服务、Prometheus、独立向量库或模型网关。预算、备份和恢复必须实际演练；预计机器配置与资料可访问性都不是已经测得的结果。
